# TMBG 3-in-1 SMS, Messenger and WhatsApp demo

The supplied TMBG instructions run in the `local` and `test` profiles for SMS, Facebook Messenger and WhatsApp. All use the configured `AiClient`, the supplied fictional customer, and one shared booking file. Keep the existing provider profiles and repository-root `.env`. Local demo settings allow four SMS segments for the full combined opening; assistant replies remain limited to two segments. Direct UDP LIVE mode still requires one segment.

## Messenger

Send a text such as `Hello` to the configured Facebook Page. The first message starts that sender's demo and returns the greeting without calling the LLM. Later messages use the same booking rules and English/Taglish templates as SMS. Choosing an offered time records a visit request; general service questions remain available afterward.

This uses the existing signed webhook at `/api/webhooks/messenger` and the existing `META_APP_SECRET`, `META_VERIFY_TOKEN`, `META_PAGE_ACCESS_TOKEN`, `META_PAGE_ID`, and `META_GRAPH_API_VERSION` settings. The Page webhook must already point to this application's public HTTPS URL. The same `OPENAI_*` settings apply. Restart the application with the `local` profile after updating the code; no separate campaign-start request or phone linking is needed for Messenger. Messenger also works when SMS is disabled.

Conversation history and duplicate-message tracking are separate for each channel, Page/account, and sender. Messenger never reads an SMS conversation. Booking references are shared. A saved preferred day does not reserve the branch's capacity or prevent another customer requesting that day. Messenger records add `channel: "MESSENGER"` and `sender_id` (the Page-scoped sender ID); `account_id` is the Page ID and `phone` remains the supplied fictional customer's phone. These demo sessions and duplicate-message records last until application restart.

## WhatsApp

In `local` and `test`, authenticated incoming WhatsApp text messages also use `TmbgBookingAssistant` instead of the legacy dealership workflow. Send a message to the configured WhatsApp number to start a separate demo session; the first message returns the greeting and later messages use the booking assistant. The existing signed `/webhooks/whatsapp` endpoint, configured phone-number ID, and provider client remain in use. The Meta app must also be subscribed to the WhatsApp Business Account. Messages outside the 24-hour reply window are ignored.

WhatsApp history is isolated by channel, account and sender. Booking references are shared with SMS and Messenger. Saved WhatsApp bookings include `channel: "WHATSAPP"`, the WhatsApp `sender_id`, and the configured phone-number ID as `account_id`; `phone` remains the supplied fictional customer's phone. Sessions reset on restart. A failed reply is retained for the next incoming turn, following the Messenger demo behavior; provider acceptance does not confirm delivery. Production retains the existing dealership workflow and requires a durable dispatcher.

## Start an SMS conversation

Send an authenticated request using a configured SMS account:

```bash
curl --request POST 'http://localhost:8080/api/v1/sms/campaign/start' \
  --header 'Authorization: Bearer <SMS_API_TOKEN>' \
  --header 'Content-Type: application/json' \
  --data '{"accountId":"goip-line-1"}'
```

`recipient` is optional and defaults to the phone in the supplied fictional customer record. To use a test handset, include its number:

```json
{"accountId":"goip-line-1","recipient":"<test handset number>"}
```

The override changes only where SMS is sent. The assistant continues to use the supplied fictional customer's vehicle, renewal, and service details. The endpoint returns `202` with an application message ID and a `Location` URL for the existing SMS status endpoint. Submission status does not confirm handset delivery. Each deliberate start sends a new greeting and resets that account/participant's demo session.

## Conversation flow

Every new SMS or Messenger conversation starts with the English `OPEN_GREETING`. Language is selected again on each turn: messages containing recognized Tagalog words use Taglish; English messages, numbers and unclear text without Tagalog default back to full English. English replies omit `po` and `opo`, including service-generated confirmations and fallbacks.

The service renders and sends `OPEN_GREETING` without an LLM call. Fresh replies from the demo participant use the supplied rules, templates, customer record, and conversation state instead of the legacy shared dealership workflow. Common greetings, thanks and wellbeing questions receive short English or Taglish acknowledgements directly. A greeting continues the current offer with one short question, or preserves the date/status question already pending. A thank-you or "you are welcome" receives a brief acknowledgement and an invitation to ask for car service help. After a confirmed booking, social-only replies say we hope to see the customer at Toyota Manila Bay soon and invite service questions. After all services are declined, they invite further help without restarting offers. These social messages never advance service decisions or restart a completed conversation. When a social opener precedes a real question, decision or date, the service processes that remaining message and prefixes a brief acknowledgement when it fits the SMS limit. Original messages remain in the conversation history. Hosted inbox polling selects the latest fresh message by `received_at` for each demo account/participant, using the receive ID to break ties. Earlier messages in the snapshot remain available in the retained inbox without triggering replies.

The service supplies the rules, negotiation playbook, curated PDF reference, service catalog, insurance estimates, customer record, derived fields, conversation state, templates and approved general answers, then asks the LLM for one JSON response. The LLM has no tools or write access. The service validates the response before enqueuing SMS and owns booking creation. Each conversation uses the supplied fictional customer. The English greeting identifies the AI assistant and vehicle, states that preventive maintenance is due this month and comprehensive insurance and registration are due for renewal, and offers to handle all three in one appointment. A clear yes accepts all three and leads to the preferred-date question. A no leaves each individual service undecided and starts separate offers: registration renewal, regular maintenance, then car insurance, regardless of earlier individual refusals or the recorded insurance status. During individual offers, only the current offer can receive a decision; the model cannot resolve unasked services or change their order.

The service derives `all_services_answered` from its own record of the offers sent and an accepted, declined or skipped answer for each. Every offer must be answered before asking for a date or saving a booking. A yes to one service does not bypass remaining offers, and two refusals do not end the conversation. After each decision, the service sends a brief acknowledgement naming the service just answered before the next offer, date question or closing, in the current English or Taglish language. Acceptance records interest and never claims the booking is confirmed. Zero accepted services ends in `COMPLETED_NO_BOOKING` without a record. One to three accepted services proceeds to date selection; only accepted services are saved. Registration renewal includes required basic insurance internally. Explicit pauses, opt-outs, wrong numbers and requests for a person interrupt progression without marking unanswered services complete. Callback and advisor requests direct the customer to dealership contact; no external action is promised. Opt-out and wrong-number suppression lasts until restart or a deliberate new start; it is not a durable or cross-channel unsubscribe registry.

After all service decisions, choosing an unambiguous day inside the supplied window (for example, `October 19 please`) confirms the customer's intent to record a visit request; no additional `Yes` is needed. A question, refusal, tentative date, time alone or ambiguous weekday does not create a booking. No appointment hour or branch capacity is promised. Saving the booking ends booking operations but leaves general service questions available. A failed save leaves booking open for another reply.

Customers can ask general dealership and service questions during booking, after confirmation, or after declining every service. The model classifies the message with `message_intent` and composes an answer grounded in the supplied reference material. Templates and `dealership/catalog.json` are factual references and fallbacks, rather than mandatory wording. A matching approved topic supplies a fallback if the generated answer is missing or fails reply validation. Knowledge replies preserve the current offer, service decisions and date-selection stage. Missing facts, unrelated questions and unsupported requests receive a limited-chat message directing the customer to contact Toyota Manila Bay directly. The chat does not invent contact details, offers or dealership facts.

After confirmation, requests to change, reschedule or cancel receive: "Bookings cannot be changed or cancelled through this chat at this time. Please contact Toyota Manila Bay directly for help." The confirmed session never re-enters booking or writes another booking through follow-up replies. Other unsupported requests receive: "This chat can only answer general service questions right now. Please contact Toyota Manila Bay directly for further help." General questions remain available afterward; this is a restricted capability, not a timed shutdown or advisor handoff. Duplicate receipts reuse their prior reply. These conversation protections follow the existing process-local session lifecycle; restarting or deliberately starting a new campaign resets that session.

There are no customer-facing letter codes or numbered reply instructions. Customers can request a day with wording such as `October 19 please`, `Monday works for me`, or `Sa October 19 na lang po`. A weekday must identify one date inside the window. Out-of-window or ambiguous choices prompt clarification using the remaining date range.

Preferred dates come from `reg_window_start` and `reg_window_end` in `sms/tmbg/customer_records_3in1.json`, inclusive. The earliest requestable day is the later of the window start and today in `Asia/Manila`. The service presents the range instead of a fixed appointment menu. The old `enrichment.slots` timestamps are removed and are no longer used. Asking for other dates repeats the remaining window. If the window has ended, no date can be saved here; the customer is directed to dealership contact.

The AI interprets date selections and returns an ISO date with `message_intent=date_selection` and `outcome=booking_requested`. The service validates that date against the offered window, current date, registration status and accepted services, without requiring the wording to match a second regex parser. Mock mode retains its local parser. Selections accept a unique date or weekday, and wording such as `October 19 would work for me`, `this coming Monday`, `tomorrow`, or `the earliest one`. Questions, tentative statements and refusals do not create bookings.

Conversation state is process-local. Restarting the application or calling the start endpoint resets the demo session. The existing SMS inbox and outbox keep their normal persistence and transmission rules.

SMS receive diagnostics in `logs/channel-connect.log` distinguish import from AI processing. New receipts log `action=QUEUED` or `action=STORED`. Stored reasons include `no_active_demo_or_authorized_identity` (start the campaign for that account/number), `before_receive_baseline`, `non_phone_sender`, and `superseded_in_snapshot` (only the latest eligible demo reply in a snapshot is processed). Repeated snapshots do not repeat successful import logs. Slow receive requests and conflicting receipt IDs log warnings; processing and gateway submission logs include elapsed milliseconds. These diagnostic lines omit phone numbers and message bodies.

## Dates and booking records

The supplied record defines an October 15-21, 2026 renewal window. The service derives requestable days using the actual date in `Asia/Manila`, including today. The window remains customer input and needs updating when that renewal period has passed; it is never shifted automatically.

Only the service writes bookings. After all three service decisions, a valid preferred date creates one JSON line in the repository-root `bookings.txt`, with a reference such as `TMB-00001`. New records store `appointment` and the legacy `slot_code` field as an ISO date (`YYYY-MM-DD`), without an invented time. They also include `services_asked` and `all_services_answered: true`. Existing timestamp records can still be read for booking references. This is a local request record, with no live scheduling, capacity, callback, or advisor delivery integration. The customer acknowledgement says the dealership must confirm the reservation and requirements. The LLM cannot create a reference or write to the file.

## Prompt and reference maintenance

`system-prompt.md` and `rules_3in1.txt` define free-text English/Taglish conversation. `negotiation_playbook.txt` covers hesitation without pressure. `service_catalog.json` supplies registration, maintenance and insurance in that order; Java enforces progression. `insurance_prices.json` leaves insurance prices and the expiry threshold unset until confirmed. Insurance is always offered third without claiming an active policy is due. Null prices never become numeric estimates. Existing `PHP` prefixes in the record are retained without duplication.

`dealership-reference.txt` integrates relevant content from the owner-supplied **Toyota Manila Bay 2.pdf**, with page references. Numbered scripts and automatic bundle pitches are replaced by the requested natural flow. Warranty outcomes, resale percentages, turnaround guarantees, legal penalties, insurer accreditation, ratings, addresses and hours from the document are not approved operational facts. The reference explains maintenance inclusions, required versus optional work, policy comparisons, and registration coordination without promising unsupported actions.

Customer-facing responses omit the word ?demo?; internal profile names, class names, routes and operational documentation retain it where it identifies the actual deployment mode. These wording changes do not enable production delivery or live dealership scheduling. Existing automated tests still contain assertions for the previous name, footer and reply-code contract; tests were neither changed nor run under repository policy.

Start this flow through `POST /api/v1/sms/campaign/start`, which sends the opening and initializes a fresh session for that account and recipient. Alternatively, send `/reset` by SMS to the configured SIM to start or restart only that sender's campaign and receive the opening again, without an AI call. The command ignores case and surrounding whitespace; additional text is treated as a normal reply. It works without an active session, including after an application restart, subject to the existing receive baseline and snapshot selection rules. Saved bookings are retained. Reset replies use the inbound receipt's existing deduplication key. The generic `/api/v1/sms/send` endpoint sends text only; it does not start or reset a campaign. For a hosted demo, keep the `local` profile active alongside the configured SMS provider profile; the profile name does not require the app to run on your PC.

Diagnostics log campaign initialization and stage transitions at INFO. DEBUG logs include interpretation classification, date rejection and fallback reasons. AI failures log the exception type and stage without messages, credentials or customer text. Structured AI output that exceeds the response limit is rejected rather than truncated into invalid JSON.

The opening retains the original AI introduction and appointment question, followed by the "Hi {{full_name}}, skip the LTO lines and broker visits!" campaign copy. Name and model placeholders come from the same customer record. With the supplied customer, the full English opening is 555 GSM-7 characters (four SMS segments). Both paragraphs describe the same three-service offer; they do not create separate consent steps. Questions about "3 in 1" preserve the offer, and clear acceptance covers all three services.
